1. Document Purpose

This PRD defines the requirements for implementing, validating, and maintaining a complete multilingual UI system for SmartCrop. The system must allow a user to select a supported language and have application-controlled visible text update throughout the application while preserving the existing UI design and dimensions.

This PRD is based on the supplied SmartCrop README, which describes the existing multilingual architecture, application portals, routes, and translation services. fileciteturn0file0L172-L179

2. Product Context

SmartCrop is an agricultural intelligence, climate distress prediction, farm credit facilitation, and government monitoring platform for multiple stakeholder groups. The README identifies Farmer, Agriculture Extension Officer, Bank & Insurance, and Government/Admin portals. fileciteturn0file0L16-L16

The existing implementation includes a UI dictionary, Google Translate integration, and Sarvam AI Indic NLP capabilities. fileciteturn0file0L176-L179

3. Problem Statement

Users may access SmartCrop in different Indian languages. The current multilingual capability must be made consistent across the full application so that language selection is global, persistent, and verifiably functional. Translation must not introduce layout changes, overflow, visual regressions, or broken interactions.

4. Goals

Support exactly 14 languages across the application.

Translate application-controlled visible UI text across all major pages and reusable components.

Preserve the existing UI design, component structure, dimensions, spacing, and responsive behavior.

Allow language selection to persist across navigation and refresh.

Use the existing centralized translation architecture where possible.

Provide English fallback for missing translations.

Validate the implementation by running the application and performing automated/manual QA.

Detect, fix, and re-test translation, visual, console, hydration, and build issues.

5. Non-Goals

Redesigning SmartCrop UI.

Changing database schemas solely for UI translation.

Translating technical identifiers, URLs, API endpoints, database field names, or internal code identifiers.

Replacing the entire existing AI, map, authentication, SMS, or database architecture.

Adding unsupported languages.

Increasing component dimensions to accommodate longer translated text.

9. Functional Requirements

FR-01 Global language switching

Selecting a language updates visible application UI without requiring manual page-by-page translation.

The current route and page state should be preserved whenever possible.

FR-02 Exact language list

The selector must contain exactly the 14 supported languages.

Removed languages must not be offered.

FR-03 Translation coverage

Translate navigation, headings, labels, buttons, forms, tables, charts, dialogs, notifications, loading states, empty states, errors, and other application-controlled UI text.

FR-04 Persistence

Selected language remains active across route navigation and browser refresh.

FR-05 Fallback

Missing translations fall back to English and never render undefined, null, empty, or broken translation keys.

FR-06 Dynamic text

Dynamic values such as names, numbers, dates, scores, and API values must remain intact while surrounding UI text is translated.

FR-07 AI content

Where supported by the existing architecture, selected language should be respected by AI/Indic translation flows.

FR-08 RTL

Urdu must be tested for correct text direction without breaking layout.

10. UI Stability Requirements

This is a mandatory product requirement: changing language changes text, not the UI design.

Card width and height must remain stable.

Button dimensions must remain stable.

Navbar height must remain stable.

Sidebar width must remain stable.

Modal dimensions must remain stable.

Table structure and dimensions must remain stable.

Chart dimensions must remain stable.

Spacing, padding, margins, grid structure, icon sizes, and responsive breakpoints must remain unchanged.

No horizontal overflow may be introduced.

No major layout shift may occur.

If translated text is too long, only typography may be adjusted: font size, line height, controlled wrapping, or related text styling. Components must not be enlarged to fit translations.

12. Technical Requirements

Do not duplicate translation logic across individual pages.

Use centralized translation keys and typed language configuration where practical.

Do not translate routes, API paths, database fields, IDs, CSS classes, or internal identifiers.

Do not blindly translate user-generated or database content.

Avoid unnecessary external translation requests for static UI text.

Avoid translation loops, duplicate DOM translation, hydration mismatch, and excessive rerenders.

Preserve authentication, RBAC, APIs, MapLibre, charts, AI, notifications, SMS, and database behavior.

13. Automated QA Requirements

The QA process must run the actual application rather than relying only on source-code inspection.

Install dependencies when required and start the development server.

Run lint, TypeScript, and production build checks.

Create/execute a route test matrix covering all available routes.

Test language switching on major pages and shared components.

Verify actual visible text changes rather than only checking language state.

Check browser console for JavaScript, React, translation, network, and hydration errors.

Check network behavior for unnecessary or repeated translation requests.

Test language persistence across navigation, back/forward navigation, direct URLs, and refresh.

Test desktop, tablet, and mobile layouts.

Deep-test English, Hindi, Odia, Bengali, Tamil, Telugu, and Urdu.

When issues are found, fix them and repeat the test cycle.

14. QA Test Loop

Required workflow:

RUN → TEST → REVIEW → IDENTIFY ISSUE → FIX → RE-RUN → VERIFY

The implementation must not be declared complete simply because code changes compile. The running application must be exercised and verified.

17. Risks & Mitigations

Risk

Mitigation

Long translated strings

Adjust typography only; preserve component dimensions.

Google Translate DOM conflicts

Prefer centralized application translations for controlled UI.

Missing translation keys

Use English fallback and audit dictionaries.

Hydration mismatch

Test refresh and SSR/client rendering; fix root causes.

Translation API overuse

Use static dictionaries for static UI and avoid repeated requests.

RTL layout breakage

Test Urdu separately across desktop/mobile.

Untranslated hardcoded strings

Perform a codebase-wide user-facing string audit.

Regression in existing features

Re-test auth, RBAC, APIs, maps, charts, AI, notifications, SMS, and database flows.

18. Deliverables

Updated multilingual implementation supporting exactly 14 languages.

Removal of the 9 excluded languages.

Application-wide translation coverage.

Automated/assisted route and language QA coverage.

Visual regression verification.

Fixed console, hydration, translation, and layout issues found during QA.

Updated README/documentation.

Final QA report containing routes tested, languages tested, issues found/fixed, and lint/TypeScript/build results.

19. Final Product Principle

LANGUAGE CHANGES TEXT — NOT THE UI DESIGN.

Translated text may require a small typography adjustment, but the existing SmartCrop layout, component dimensions, spacing, positioning, and responsive structure must remain stable.
