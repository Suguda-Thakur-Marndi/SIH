# Product Requirements Document
## SmartCrop — SMS / Notification Distress Alert System

**Parent Problem Statement:** PS-02 | Smart Crop — Advisory & Farmer Distress Early-Warning Platform
**Category:** Software | **Theme:** Agriculture, FoodTech & Rural Development
**Version:** 1.0 | **Status:** Draft (Hackathon Build) | **Scope:** Backend-only — no SMS frontend

---

## 1. Purpose

Close the loop on SmartCrop's core distress cycle by automatically alerting a farmer the moment the platform detects agricultural or financial distress — **without requiring the farmer to open the app**.

```
MONITOR → DETECT → PREDICT → EXPLAIN → INTERVENE
```

becomes

```
MONITOR → DETECT → PREDICT → EXPLAIN → ALERT (SMS) → INTERVENE
```

This is the low-bandwidth delivery channel the parent PRD calls out under §5.6 (Disaster Warning) and §5.10 (Multilingual Voice/Text Delivery) — this document is its implementation spec.

## 2. Scope

**In scope**
- Backend service that evaluates a farmer's distress risk score and disaster feeds, decides whether to alert, and sends an SMS
- Deduplication / threshold-crossing logic so farmers aren't spammed
- Localized (English / Hindi / Odia) message generation via the existing Sarvam AI integration
- Persistence of every notification + delivery status in the existing `notifications` table
- Parallel alert path to the Officer Command Center
- One SMS provider integration (MSG91 or Exotel), behind a provider-agnostic interface

**Explicitly out of scope**
- Any new farmer-facing SMS UI, opt-in screen, or SMS composer — none is being built
- Voice/IVR calls (stretch goal only, not MVP)
- Multi-provider failover (stretch goal only)
- Push notifications (stretch goal only)

**Why backend-only:** the farmer already has a phone number, language, and risk score on file. The backend can decide everything — whether to alert, why, in what language, using which template — without any new screen. The only farmer-facing artifact is the SMS itself; the existing `/notifications` page remains an optional in-app mirror of the same event.

## 3. Goals & MVP Success Criteria

The feature is complete when this single scenario works end-to-end:

1. Farmer has a registered phone number, language, crop, and location on file
2. Monitoring data (rainfall, market, loan, soil, NDVI) produces a distress score
3. Score crosses the 70 threshold
4. Backend detects the crossing (not just "score is high")
5. A `notifications` row is created (`channel = SMS`, `status = PENDING`)
6. A localized message is generated from a verified template
7. The SMS provider sends the message and the row is updated (`status = SENT`)
8. The farmer receives the SMS **without opening SmartCrop**
9. The officer sees the same farmer appear in the high-risk queue
10. Re-running the check at the same score does **not** send a duplicate SMS

```
                 │

             📱 Farmer's Phone

  In parallel ─────────────────────────────►  notifications table (AWS RDS MySQL)
                                               + delivery status
                                                       │

```

**Fits into the existing stack** — no new backend is introduced:

| Layer | Uses |
|---|---|
| Runtime | Next.js Route Handlers (Node.js runtime), same as the rest of `/app/api` |
| Database | AWS RDS MySQL, via the existing `lib/db.ts` singleton pool (`mysql2/promise`) |
| Language | Sarvam AI, via the existing `lib/sarvam-ai.ts` client |
| Scheduling | GitHub Actions cron, same mechanism already used for weather/mandi refresh |
| Auth | Existing JWT (`smartcrop_token`) + RBAC proxy middleware, plus a new `CRON_SECRET` for machine-to-machine calls |

## 5. Alert Categories

### A. Distress Risk Alerts
Generated by the existing Risk Engine from the three core hackathon signals (rainfall deviation, market price drop, loan due-date proximity), plus soil/NDVI as secondary signals.

| Risk Score | Action |
|---|---|
| < 50 | No SMS |
| 50–69 | In-app advisory only, no SMS |
| Crosses 70 (from below) | Send **HIGH** SMS |
| Crosses 85 (from below) | Send **CRITICAL** SMS |
| Stays above threshold | Do **not** resend |
| Drops below then rises again | Send a new alert |

### B. Disaster Alerts
Bypass the risk-score threshold entirely — an authoritative warning (cyclone, flood, extreme rainfall, heatwave) for the farmer's district triggers an immediate SMS regardless of their current risk score.

### C. Officer-Triggered Alerts
An officer can manually push an emergency SMS to a specific farmer from the Command Center; this reuses the same `/api/notifications/emit` path and bypasses cooldown.

## 6. Message Generation Rule

Verified data → template → (translation if needed) → SMS. The LLM is never in the send path.

```
Risk Engine → verified reasons → message template → Sarvam translation → SMS   ✅
LLM invents a warning → SMS                                                     ❌
```

This mirrors the parent PRD's non-negotiable rule that agronomic/financial facts come from curated data and rules — the LLM only explains, it never decides. §27 note: do not let any AI layer trigger an SMS directly; it may only translate or phrase what the rules engine already decided.

### Templates (kept short — full detail stays on the website)

**English — HIGH**
```
SmartCrop Alert: Your farm is at HIGH RISK ({{score}}/100).
Main concerns: {{reason1}}, {{reason2}}.
Check today's advisory in SmartCrop or contact your agriculture officer.
```

**Hindi — HIGH**
```
SmartCrop चेतावनी: आपके खेत का जोखिम स्तर HIGH ({{score}}/100) है।
मुख्य कारण: {{reason1}}, {{reason2}}।
आज की सलाह के लिए SmartCrop देखें या अपने कृषि अधिकारी से संपर्क करें।
```

**Odia — HIGH**
```
Same verified structure, translated through the existing Sarvam AI Indic pipeline
(lib/sarvam-ai.ts) — no separate translation system is introduced.
```

Cache translated templates per (template, language) pair rather than re-translating identical content on every send (`HIGH_RISK_TEMPLATE_OD`, `CRITICAL_RISK_TEMPLATE_OD`, `CYCLONE_TEMPLATE_OD`, `FLOOD_TEMPLATE_OD`, `HEATWAVE_TEMPLATE_OD`).

**Disaster template (English)**
```
SmartCrop Disaster Alert: Heavy rainfall/flood conditions expected in your area.
Follow local safety instructions and protect farm equipment where possible.
```

**Officer copy (more technical, sent in-app / dashboard, not SMS)**
```
Farmer {{name}} — HIGH RISK {{score}}/100.
Primary factors: {{reason1}}, {{reason2}}.
Recommended action: contact farmer / schedule visit.
```

## 7. Deduplication & Cooldown

Without deduplication, an hourly risk-check job would re-send the same alert every run. Rule: send only on a **severity-level crossing**, not on every score recalculation.

```
Day 1 → 62 → no SMS
Day 2 → 68 → no SMS
Day 3 → 72 → HIGH-RISK SMS  (crossed 70)
Day 4 → 75 → no duplicate   (still HIGH)
Day 5 → 81 → no duplicate   (still HIGH)
Day 6 → 87 → CRITICAL SMS   (crossed 85)
```

| Alert type | Cooldown |
|---|---|
| HIGH | 24 hours |
| CRITICAL | 12 hours |
| DISASTER | Immediate, deduplicated per warning event rather than by time |

A new alert also fires if the score falls back below threshold and later crosses it again — this is a genuinely new event, not a repeat.

## 8. Data Model

Extend the existing `notifications` table — do not create a second/parallel notification system.

```sql
-- Add if not already present on the existing `notifications` table
ALTER TABLE notifications
  ADD COLUMN channel              ENUM('SMS','IN_APP','VOICE','PUSH') NOT NULL DEFAULT 'IN_APP',
  ADD COLUMN status                ENUM('PENDING','SENT','DELIVERED','FAILED') NOT NULL DEFAULT 'PENDING',
  ADD COLUMN provider              VARCHAR(50)   NULL,
  ADD COLUMN provider_message_id   VARCHAR(100)  NULL,
  ADD COLUMN risk_score            INT           NULL,
  ADD COLUMN reason                TEXT          NULL,
  ADD COLUMN retry_count           INT           NOT NULL DEFAULT 0,
  ADD COLUMN last_error            TEXT          NULL,
  ADD COLUMN sent_at               DATETIME      NULL,
  ADD COLUMN delivered_at          DATETIME      NULL,
  ADD COLUMN failed_at             DATETIME      NULL;
```

Target shape after the migration:

| Field | Notes |
|---|---|
| `id`, `user_id`, `farmer_id`, `type`, `title`, `message`, `created_at`, `is_read` | Already exist |
| `type` | `DISTRESS \| DISASTER \| WEATHER \| MARKET \| LOAN \| OFFICER \| GENERAL` |
| `priority` | `LOW \| MEDIUM \| HIGH \| CRITICAL` |
| `channel` | `SMS` for this feature |
| `status` | `PENDING → SENT → DELIVERED`, or `→ FAILED` |
| `provider` / `provider_message_id` | Which vendor sent it, and their message ID (for webhook matching) |
| `risk_score`, `reason` | Snapshot of the score and top contributing factors at send time |

**Reading the previous score for threshold-crossing detection:** reuse the existing `risk_scores` / `crop_risk` table (already populated by the Risk Engine per the parent PRD) — pull the two most recent rows per farmer to compare current vs. previous severity band. No new table is needed for this.

### `lib/notifications/types.ts`
```ts
export type NotificationType =
  | "DISTRESS" | "DISASTER" | "WEATHER" | "MARKET" | "LOAN";

export type Priority = "LOW" | "MEDIUM" | "HIGH" | "CRITICAL";

export type NotificationEvent = {

  type: NotificationType;
  priority: Priority;

```

Keeping the event shape generic means voice/push can be added later without touching the Risk Engine.

## 10. Notification Service Flow

```
risk score generated
        │
   score ≥ threshold? ──No──► do nothing
        │Yes
   equivalent alert already sent (cooldown active)? ──Yes──► skip
        │No
   generate localized message from template
        │
   create `notifications` row (status = PENDING)
        │
   call SMS provider adapter
        │
   update row: SENT or FAILED (+ provider_message_id / last_error)
```

```ts
// lib/notifications/service.ts (shape)
async function processRiskAlert(farmer: Farmer, risk: RiskResult) {
  const priority = getRiskPriority(risk.score);        // rules.ts
  if (!priority) return;

  const alreadySent = await hasRecentEquivalentAlert(
    farmer.id, "DISTRESS", priority
  );
  if (alreadySent) return;

  const message = await buildLocalizedRiskMessage(farmer, risk); // templates.ts + sarvam-ai.ts

  const notification = await createNotification({
    farmerId: farmer.id,
    type: "DISTRESS",
    channel: "SMS",
    priority,
    message,
    riskScore: risk.score,
  });

  await sendSms({ phone: farmer.phone, message, notificationId: notification.id }); // sms.ts
}
```

## 11. Provider Abstraction

Keep the vendor behind a small interface so the rest of the app never depends on one provider directly:

```
Notification Service
        │
  SMS Provider Interface
   ├── MSG91
   ├── Exotel
   └── Twilio
```

For an India-focused SIH prototype, **MSG91 or Exotel** is the practical default (Indian mobile numbers, INR pricing, DLT-compliant templates). **Implement one provider for the hackathon build** — the interface is what makes swapping later cheap, not parallel implementations now.

```env
SMS_PROVIDER=msg91
MSG91_AUTH_KEY=your_key
MSG91_TEMPLATE_ID=your_template_id
MSG91_SENDER_ID=SMARTC
```

Never prefix these with `NEXT_PUBLIC_` — they are server-side secrets, read only inside `lib/notifications/sms.ts`.

Build on the notification endpoints the README already documents rather than introducing a competing system.

### Internal endpoint protection
```
Authorization: Bearer <CRON_SECRET>
```
`/api/risk/check-all`, `/api/disaster/check`, and `/api/notifications/webhook` must never be publicly callable without this check — they can trigger real SMS sends to real people.

## 14. Scheduled Risk Checking

Same mechanism already used for weather/mandi data refresh — GitHub Actions cron, not a new job runner.

```
GitHub Actions (cron)
        │
POST /api/risk/check-all   (Authorization: Bearer CRON_SECRET)
        │
fetch monitored farmers → recalc risk → detect threshold crossing → Notification Service → SMS
```

A practical demo cadence is every 6 hours, with the ability to trigger the job manually for the live demo.

## 15. Disaster Alert Flow

```
Disaster feed (IMD-style warning) → warning for district
        │
find farmers in affected region
        │
dedup check (per warning event, not per farmer score)
        │
translate template → send SMS → store delivery status → update officer dashboard
```

Only include safety instructions sourced from an authoritative feed or the project's curated disaster rules — never LLM-generated.

## 16. Officer Notification Path

Every distress event fans out to two independent delivery paths so a provider failure on one never blocks the other:

```
                DISTRESS EVENT
                      │
        ┌─────────────┴─────────────┐
        ▼                           ▼
   Farmer SMS                Officer Alert
   (short, plain)             (technical, in dashboard)
```

## 17. Delivery Status & Failure Handling

States: `PENDING → SENT → DELIVERED`, or `SENT → FAILED`. If the provider supports delivery webhooks, `/api/notifications/webhook` updates `status = DELIVERED`. **For the MVP, `SENT` is an acceptable terminal state** if webhook wiring becomes time-consuming — do not block the demo on it.

SMS failure must never take down the Risk Engine — the two are loosely coupled:

```
risk calculated successfully → notification row created → SMS attempt
        │
   attempt fails → retry (max 3) → still fails → status = FAILED, last_error stored
        │
   officer still sees the farmer's risk regardless of SMS outcome
```

## 18. Security Checklist

- Provider credentials (`MSG91_AUTH_KEY`, `EXOTEL_API_KEY`, `TWILIO_AUTH_TOKEN`) — server-side env vars only, never `NEXT_PUBLIC_*`
- `/api/risk/check-all`, `/api/notifications/webhook`, `/api/disaster/check` — protected by `CRON_SECRET` / provider signature, not open endpoints
- RBAC (reusing the existing `proxy.ts` middleware): farmers see only their own notifications; officers see alerts for their jurisdiction and can manually trigger an emergency alert; admins manage notification configuration
- No SMS provider credentials or farmer PII stored anywhere client-side

## 19. Minimal MVP — Build Only This

1. Farmer phone number + language on the farmer profile
2. Risk score + threshold detection (reusing the existing Risk Engine)
3. `notifications` row creation on threshold crossing
4. One SMS provider integration
5. Message templates (English required; Hindi/Odia via Sarvam AI if time permits)
